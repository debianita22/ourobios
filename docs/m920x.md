# ThinkCentre M920x Tiny

From v1.4.0 each version also has a release for the **Lenovo ThinkCentre
M920x Tiny** (Intel Coffee Lake, Q370), `vX.Y.Z-m920x-fsp`, built from the
same tree as the W541 ones: coreboot's `lenovo/m720q_m920q` board with
patches 0136-0179, the same EDK II payload and setup menu, vboot with two
signed RW slots, signed UEFI capsules and fwupd. The board is in
`boards/m920x/`: its defconfig, flash map, blobs and the checks of
`tools/verify-rom.sh`.

## Status

The M920x releases are **pre-releases** until they are confirmed on the
machine. The CI checks them as it checks the W541 ones: the bytes before the
BIOS region (descriptor, GbE, ME) against `boards/m920x/intel.sha256`, the
flash map, the cache-as-RAM layout of the read-only part
(`boards/m920x/ro-interface.txt`), both signed slots, the setup menu
(`tools/build.sh menu`) and the payload in QEMU (`tools/build.sh smoke`).
None of that runs the coreboot of the M920x: the first boot is on real
hardware.

## What is different from the W541

- **One variant, `fsp`**: the RAM is trained by Intel's FSP-M for Coffee
  Lake (coreboot's `3rdparty/fsp`), as in every coreboot build for this
  machine; `mrc.bin` and the native RAM init are Haswell only.
- **ESRT GUID** `2e0b05d4-27d0-4faa-929d-93989c01fee8`: a W541 capsule or
  fwupd package is refused on an M920x and the other way round; the
  project's fwupd remote carries both, and fwupd offers each machine its
  own.
- **Intel ME**: the whole CSME 12 firmware, no `me_cleaner`
  ([Intel ME](#intel-me)).
- **Read-only part**: bootblock with verstage and the microcode of the
  Coffee Lake processors (`06-9e-0a` to `06-9e-0d`); FSP-M and FSP-S are in
  each slot, so a capsule updates them too.
- **Display**: with vboot, coreboot's graphics code for Intel SoCs turns the
  screen on only when vboot asks; here it is always on
  (`CONFIG_VBOOT_ALWAYS_ENABLE_DISPLAY`).
- **Setup menu**: *General* (*About this ThinkCentre*, with the state of
  the Intel ME from v1.4.0; *Boot*, [Boot options](#boot-options)), *Energy
  Saver* (Hyper-Threading, SpeedStep, Turbo Boost, PL1 and PL2, *After a
  power loss*, *Wake on LAN from off*), *Hardware* (Intel graphics,
  *Cooling*: the fan mode of the EC and, from v1.4.0, the TCC activation
  offset, [Fan](#fan); *Devices*: Ethernet, audio, Wi-Fi, front and rear
  USB ports, the PCIe riser slot), *Security* (*Flash protection*,
  *Memory protection*, VT-d, *Management Engine*), *Compatibility*
  (macOS: ACPI processor objects and C-state configuration lock,
  [docs/macos.md](macos.md#thinkcentre-m920x); the 8254 timer) and
  coreboot's *Console*. The EC in the Super I/O only runs the fan, so no
  battery or keyboard options; the board has no PS/2 port.
- **Settings reset**: from v1.4.0 an RTC power loss (a CMOS clear) resets the
  setup options, as with the Lenovo firmware
  ([Resetting the settings](#resetting-the-settings)); on the W541 they
  stay.
- **Memory training across updates**: from v1.4.0 the capsules write the two
  slots only and the training stays ([Updates](#updates)); on the W541 a
  capsule empties `RW_MRC_CACHE`.

## Flash layout

Two SPI chips on the mainboard, marked BIOS1 (W25Q128JV, 16 MiB) and BIOS2
(W25Q64JV, 8 MiB), seen as one 24 MiB space. The map is
[`boards/m920x/flash.fmd`](../boards/m920x/flash.fmd):

| Range | Chip | Contents |
|---|---|---|
| `0x0000000-0x0BFFFFF` | BIOS1 | descriptor, GbE, Intel ME: the same in every release, from `boards/m920x/blobs/` |
| `0x0C00000-0x0CBFFFF` | BIOS1 | `RW_MRC_CACHE`, `SMMSTORE`, `RO_VPD`, `RW_ELOG`, `RW_NVRAM`, `RECOVERY_MRC_CACHE`: written at runtime, empty in the image |
| `0x0CC0000-0x11DFFFF` | both | `RW_SECTION_A`: slot A (romstage, FSP-M, FSP-S, ramstage, payload), signed |
| `0x11E0000-0x16FFFFF` | BIOS2 | `RW_SECTION_B`: slot B, the same |
| `0x1700000-0x17FFFFF` | BIOS2 | `WP_RO`: FMAP, vboot's root key, bootblock with verstage, microcode |

The descriptor, GbE and ME come from the Lenovo firmware of the M920x the
blobs come from, read from its two chips
([`boards/m920x/blobs/README.md`](../boards/m920x/blobs/README.md)): the
descriptor with its regions unlocked (every master reads and writes every
region) and Lenovo's region bounds, so `--ifd -i bios` writes the same
range under either descriptor.

## First install

**From another coreboot**, with the flash unlocked (the case of the
machine these blobs come from): only the BIOS region, which keeps the
machine's own descriptor, ME and MAC address. As on the W541, the kernel
must release the SPI controller first
([docs/flashing.md](flashing.md#before-you-start)), but on this PCH the
controller is a PCI device (`00:1f.5`) and its module is `spi_intel_pci`,
not `spi_intel_platform`. Secure Boot must be off in the firmware that
runs: with it on, the kernel's lockdown keeps flashrom away from the
hardware.

```sh
sha256sum -c SHA256SUMS --ignore-missing
cat /sys/kernel/security/lockdown                        # [none]: Secure Boot is off
sudo modprobe -r spi_intel_pci spi_intel
sudo flashrom -p internal -r backup-$(date +%F).rom      # 25165824 bytes, keep it off the machine
sudo flashrom -p internal --flash-name 2>&1 | grep -E 'FREG|PR[0-4]:|locked|mtd'
sudo flashrom -p internal --ifd -i bios -w m920x-coreboot-vX.Y.Z-fsp.rom
```

A backup of 16777216 bytes is BIOS1 alone: flashrom went through
`/dev/mtd0`, so unload the modules and read again. Before writing, the probe
must show no Protected Range (`PRn: Warning: ... is read-only`) over the
BIOS region, `0x00c00000-0x017fffff`, and no region that is not read-write
(`FREGn: ... is read-only`, or `locked`): flashrom can erase and write the
blocks before it, stop there and leave half an image. Turn off whatever set
it in the firmware that runs (*Firmware protection* in ouroBIOS) and reboot
first. flashrom 1.4 also warns that setting the BIOS Control register failed
and that the SPI configuration is locked down: with every region read-write
and no Protected Range both are harmless, and the write goes through.

Over a coreboot built for the M920q (`lenovo/m720q_m920q`, coreboot's or
MrChromebox's), flashrom refuses the image as one for another board: the
firmware that runs is *LENOVO ThinkCentre M920 Tiny*, the image *LENOVO
ThinkCentre M920x Tiny*. On an M920x that is expected: write with
`-p internal:boardmismatch=force` in place of `-p internal`.

flashrom must end with `VERIFIED`. If it does not, do not power off: write
the image, or the BIOS region of the backup, again straight away. The UEFI
settings and boot entries start from scratch: install the boot loader at
the fallback path first
([docs/flashing.md](flashing.md#boot-loader-fallback-path)), and write the
[VPD](#serial-number-and-machine-type-vpd) afterwards.

**From the Lenovo firmware** the descriptor is locked (the CPU cannot
write it nor the ME region), and coreboot's page for the board notes that
internal flashing from the Lenovo firmware has not been tried: the first
time needs an external programmer. Read both chips twice and compare, then
build the image from your own backup, so that the machine keeps its
descriptor (unlocked with `ifdtool`), ME and MAC address:

```sh
cat bios1.rom bios2.rom > lenovo.rom                       # 16 + 8 MiB
util/ifdtool/ifdtool -p cnl -u lenovo.rom                  # -> lenovo.rom.new, regions unlocked
head -c 12582912 lenovo.rom.new > mine.rom                 # your IFD, GbE, ME
tail -c 12582912 m920x-coreboot-vX.Y.Z-fsp.rom >> mine.rom # the BIOS region of the release
head -c 16777216 mine.rom > mine-bios1.rom
tail -c 8388608 mine.rom > mine-bios2.rom
```

Then write `mine-bios1.rom` on BIOS1 and `mine-bios2.rom` on BIOS2, with
the power adapter disconnected (both chips are 3.3 V):

```sh
sudo flashrom -p ch341a_spi -w mine-bios1.rom
sudo flashrom -p ch341a_spi -c "W25Q64JV-.Q" -w mine-bios2.rom
```

That keeps the Lenovo ME as it was (version and state); the release images
carry the one of [Intel ME](#intel-me).

## Updates

On an M920x that already runs ouroBIOS, as on the W541
([docs/update.md](update.md)): the capsule from Linux, or fwupd with the
project's remote.

```sh
curl -LO https://raw.githubusercontent.com/debianita22/ourobios/main/tools/update.py
sudo python3 update.py status
sudo python3 update.py stage --latest --pre       # pre-releases until the M920x is confirmed
sudo systemctl reboot
```

The firmware checks the signature, writes the slot that is not running and
starts again on it; vboot goes back to the old slot if the new one does not
verify or does not boot.

From v1.4.0 the capsule names the two slots only, and the memory
training stays (`BOARD_CAPSULE_REGIONS` of `boards/m920x/board.sh`): the
new slot reads `RW_MRC_CACHE` and trains again only if the cache was made
with another FSP-M, another processor or Hyper-Threading the other way, as
its version says (patch 0173), about 40 s with a dark screen; otherwise
the update costs no training. The first update from rc3 or earlier
usually trains once, as those slots keyed the cache with the FSP-M
revision alone (`MRC: version mismatch: 7007420 vs 7007430` expected on
the machine of the port, whose saved `hyper_threading` option is on). The cache also stays
with `update.py other-slot`, unless `--retrain`, and with *Go back to* in
the setup when the slot that runs is v1.4.0 or later (patch 0179); a capsule
of rc1-rc3, staged to go back with `update.py rollback` or `stage
--allow-older`, still empties it. Should a new slot fail twice in a row
with the saved training, so that vboot comes back, write it once more
with a fresh one, `update.py other-slot --retrain`
([docs/update.md](update.md#a-release-from-its-image-in-the-other-slot)).

An `update.py` from before v1.4.0 refuses these capsules (*la capsula
scrive ..., attese ...*): download it again, from the commit that the
notes of the release link. From v1.4.0 `update.py status` also shows the
state of the ME and of the flash protection.

With flashrom, turn off *Firmware protection* (*Security* → *Flash
protection*) first, and copy the [VPD](#serial-number-and-machine-type-vpd)
into the new image, as on the W541
([docs/flashing.md](flashing.md#internal-update)), with Secure Boot off and
`spi_intel_pci` in place of `spi_intel_platform`
([First install](#first-install)). `--ifd -i bios` writes the whole BIOS
region with what the image has: besides the slots and the read-only part,
it empties `SMMSTORE` (settings, boot entries, Secure Boot keys, setup
password), `RW_ELOG`, `RW_MRC_CACHE` (the first boot trains), `RW_NVRAM`
(vboot's state) and, without the copy, `RO_VPD`. Before writing, `sudo
python3 tools/update.py protection` reads the protection of this boot from
the registers of the SPI controller, without writing anything: its
`WP_RO:` line must say *NON protetta* and its `BIOS Lock:` line *spento*
([docs/update.md](update.md#flash-protection)).

## Recovery

If the machine does not boot after a flash, write BIOS2 externally with the
`-8mb-chip.rom` of a release, or the last 8 MiB of a backup of ouroBIOS: it
holds the read-only part and slot B, enough to boot. Slot A, which also
takes the end of BIOS1, does not verify until it is written again, and
vboot boots slot B. BIOS1 needs writing only if it was changed;
`-16mb-chip.rom` carries the descriptor, ME and **MAC address of the
machine the blobs come from**, so build it from your own backup instead:

```sh
tail -c 8388608 backup.rom > backup-bios2.rom          # 0x1000000-0x17FFFFF
head -c 16777216 backup.rom > backup-bios1.rom         # 0x0000000-0x0FFFFFF, if needed
sudo flashrom -p ch341a_spi -c "W25Q64JV-.Q" -w backup-bios2.rom
```

The backup of another firmware goes back on both chips. A coreboot that is
not ouroBIOS has a map of its own, and its BIOS region can start in BIOS1:
on the machine of the port, MrChromebox's coreboot had its console, memory
training, `SMMSTORE`, `RO_VPD` and FMAP at `0xF00000-0xFB4FFF` and its CBFS
from `0xFB5000` to the end of BIOS2, so its last 8 MiB alone do not boot;
`cbfstool backup.rom layout -w` shows where a backup has them. Externally,
write `backup-bios1.rom` on BIOS1 and `backup-bios2.rom` on BIOS2; while
ouroBIOS still boots, `flashrom --ifd -i bios -w backup.rom` as in
[First install](#first-install) is enough (with `boardmismatch=force` for a
coreboot of the M920q).

A capsule update cut short does not need this: vboot boots the old slot
([docs/vboot.md](vboot.md)).

## Intel ME

The ME region is Lenovo's: the whole Intel CSME 12 firmware (12.0.6.1120,
PMC 300.2.11.1015) of the machine the blobs come from, no `me_cleaner`, so
the AMT, PTT and the other CSME applications are there, as with the Lenovo
firmware. *Security* → *Management Engine* →
*Intel Management Engine* turns it off and on: coreboot's CSE code sends
the MKHI command over HECI (*Disabled*: the CSME's soft temporary disable)
and resets the machine, at most three times if the state does not change.

With *Disabled*, from the next boot, the HECI interface (PCI `00:16.0`) is
gone by the time the OS starts: `lspci -s 00:16` lists nothing, and Linux
has no `mei` devices nor `/dev/mei0` (with the ME on, `mei_me` binds it,
and `mei_hdcp` and `mei_pxp` serve `i915`). It is hidden from the OS only:
coreboot reads the CSME's status earlier in the boot, and sends it the
command that turns it back on once *Enabled* is saved.

```sh
sudo cbmem -1 | grep -E 'me_state|Operation Mode'
#   CMOS: me_state = 1                     Disabled in the setup menu
#   ME: Current Operation Mode      : 3    the soft temporary disable; 0 with the ME on
```

From v1.4.0 the setup shows the state too, in *General* → *About this
ThinkCentre* → *Management Engine* (patch 0176): *Disabled (soft temporary
disable)*, *Enabled*, *Enabled, not ready (state N)*, *Security override
(jumper)* or *(HECI message)*, *Debug*, *Mode N*, or *Not available* when
HECI cannot be read. Its help has the six status registers (HFSTS1-6), the
working state, operation mode and error code and, when the ME is not in
the state that the option asks for, what to do. coreboot reads them once,
while it writes the tables, without a message to the ME, and also puts
them in two SMBIOS OEM strings, which the OS reads without HECI:

```sh
sudo dmidecode -t 11
#   String 1: ME: Disabled (soft temporary disable)
#   String 2: ME HFSTS: 80032044 368A0106 00000030 00004000 00000000 C0000004
sudo python3 tools/update.py status | grep '^ME'
#   ME:        disattivata (soft temporary disable), stato di lavoro 4, codice di errore 2; HECI (00:16.0) nascosta al sistema
```

After a [settings reset](#resetting-the-settings) the option is back on
*Enabled*.

- Do not update it with Lenovo's or Intel's tools: they expect the Lenovo
  firmware, and a failed ME update can leave the machine without a boot
  until BIOS1 is written externally.
- 12.0.6 predates the CSME fixes Intel published from November 2019
  (INTEL-SA-00241 and later). A newer CSME 12 image goes in by replacing
  `boards/m920x/blobs/me.bin` (`tools/verify-rom.sh` then wants a new
  `boards/m920x/intel.sha256`).
- The region also carries the CSME's own data (its file system), as it was
  on that machine when it was read. An image written whole, with
  `-16mb-chip.rom`, gives another M920x that state; `--ifd -i bios` never
  touches it.

## Resetting the settings

The setup options are UEFI variables in `SMMSTORE`, not CMOS bytes, so
clearing the CMOS alone would leave them as they are. From v1.4.0,
when the RTC loses power, coreboot deletes them early in the boot, before
the memory training reads the first of them, and the setup writes back
each default (patch 0175, `DRIVERS_EFI_RESET_OPTIONS_ON_RTC_FAILURE` in
the defconfig): the way back when a setting keeps the machine from
reaching the setup, as with the Lenovo firmware. While the setup still
opens, F9 (*Load Defaults*) and F10 do the same for its options, and the
clock stays.

1. Shut the machine down and unplug the power adapter.
2. Take the coin cell (CR2032) out of its holder for about a minute, or
   use the clear-CMOS jumper, then put it back.
3. Power on, and set the date and time again (an OS with NTP does it).
   The ME comes back on, so the boot after the reset restarts once or
   more (below).

The boot log of the first boot says so, and the event log has an *RTC
Reset* event (`tools/elog.py`); `tools/hw-report.py` reports the line as
an `INFO` event:

```sh
sudo cbmem -1 | grep -E 'Setup options|RTC: power failure'
#   Setup options: 31 reset to defaults (RTC power lost)
#   RTC: power failure cleared, GEN_PMCON_B: ...
```

The number is how many options had been saved. Every setup option goes
back to its default, among them:

- *Intel Management Engine*: *Enabled*. An ME that was turned off runs
  again: at the next boot coreboot turns it on and restarts the machine,
  and the OS has HECI again. FSP or the ME may also restart the first
  boot. Set it to *Disabled* again if you had it so ([Intel ME](#intel-me)).
- *Firmware protection*: on. Turn it off again before writing the flash
  from Linux (`flashrom --ifd -i bios`): with it on, the write stops at the
  protected read-only part and can leave half an image.
- *BIOS Lock*: off. *Console Log Level* and *Serial Console*: their
  defaults, from ramstage of that boot on (the console before it already
  ran with the old values).
- *General* → *Boot*: iPXE, CSMWrap and USB drives on, so their boot
  entries come back if they had been turned off
  ([Boot options](#boot-options)).
- The rest at their defaults too: *TCC activation offset* 0, *PCIe riser
  slot* Auto, the power limits of the processor, the devices on.

The other UEFI variables have other GUIDs and stay: the other boot entries
and their order, the Secure Boot keys and state, the setup password, the
boot splash and the scale of the UI. So do the VPD (serial number, Windows
key) and the event log.

- With a flat coin cell, every loss of AC power resets the settings, and
  turns the ME back on. Replace the cell.
- Only slots built with it do this: a capsule writes one slot, and until
  both slots run v1.4.0 or later, an RTC power loss on a boot of the
  older slot resets nothing there (the next boot of a newer slot may do
  it).
- A store that coreboot does not find whole (a write cut short, which the
  payload repairs) is left alone, and the next boot tries again.
- Before the first update to v1.4.0 or later, check that bit 2 of the
  second word (`RTC_PWR_STS`) is clear, `0x2200` here. The coreboot of
  earlier releases does not clear it: if it is set, the first boot of the
  new release resets the settings.

  ```sh
  sudo cbmem -1 | grep GEN_PMCON
  #   GEN_PMCON: d8a01608 00002200
  ```

Not yet tried on the machine.

## Fan

The fan is run by the EC in the Super I/O, a Nuvoton NCT6686D with
Lenovo's firmware (`M1UCT17A` on the machine tried; `sudo cbmem -1`
prints it in hex, `OEM version:4d31554354313741`), the Intelligent
Cooling Engine (ICE) of the OEM setup. ouroBIOS leaves the fan curves to
the EC's own tables: it gives the EC the temperatures they follow, and
tells it the platform at every boot.

- **Temperatures**: the CPU fan follows `PECI 0.0`, the processor
  through PECI, and takes diode 1 (`TD1P`) as the ambient temperature.
  The NCT6687D driver of coreboot writes the sources of all 32 channels
  from the devicetree and locks them; up to rc2 the board set none, so
  every channel read 0 °C and the fan stayed at its floor, about 850 rpm,
  while the CPU went to 95-100 °C under load. The devicetree now sets
  the sources the EC firmware has itself (patches 0150, 0152).
- **Platform**: at every boot, not when resuming from S3, ouroBIOS writes
  three registers of the EC (`0xA7D`-`0xA7F`) as Lenovo's firmware does:
  a Tiny board, whether a card is on the PEG slot (NVIDIA or not), the TDP
  class of the processor, the ICE mode and the policy after a power
  loss, with the boot flag that makes the EC load its profile for them,
  temperature sources and fan tables (patches 0151, 0153). The console
  log shows them: `EC: platform 42 42 07 (TDP 65 W)` with an i3-8100 and
  no card. Never told, the EC keeps the profile of its defaults, which is
  for a 35 W processor.
- **Fan mode**: *Hardware* → *Cooling* → *Fan mode (ICE)*, the ICE
  Performance Mode of the OEM setup. Measured on an M920x with an
  i3-8100, four threads of load, the profile loaded at runtime:

  | Mode | Idle (CPU 45 °C) | CPU at 94 °C |
  | --- | --- | --- |
  | Better acoustics (default) | about 850 rpm | about 3000 rpm (PWM 125 of 255) |
  | Better cooling | about 1400 rpm | about 3700 rpm |
  | Full speed | about 7500 rpm (PWM 255) | the same |

  In both automatic modes the CPU reaches 94-95 °C after 50-80 s of full
  load, below its TjMax of 100 °C: the EC lets it run warm, as with the
  OEM firmware. *Full speed* is for a hot room or a long load, and so is
  the offset below.
- **TCC activation offset**: *Hardware* → *Cooling* → *TCC activation
  offset* (from v1.4.0, patch 0177), as in the OEM setup: the processor
  throttles that many °C below its TjMax, 0 to 15, default 0 as the OEM
  firmware. Above 0 it runs cooler, with a quieter fan, under a long load,
  at a lower frequency, at times below the base one. coreboot writes it
  into MSR 0x1A2 before the processors start, at every boot and on S3
  resume, and gives it to FSP-S; it is not locked, so Linux can still
  change it (the `intel_tcc_cooling` cooling device). Listed only when the
  processor can take it (bit 30 of MSR 0xCE). Not yet tried on the
  machine:

  ```sh
  sudo modprobe msr && sudo rdmsr -f 29:24 0x1a2     # the offset in use (msr-tools)
  ```

To read the fan and the temperatures under Linux, `sudo modprobe nct6683`
(it knows the EC, customer ID 0x0201): `fan2`, `pwm2`, and `PECI 0.0`,
`PCH CHIP`, `Diode 0 (curr)` to `Diode 2 (curr)`. Lenovo's SIO firmware
update (`M1UCT18A`, for Windows) only changes the fan tables of the tower
models.

## Boot options

*General* → *Boot* in the setup: switches that the payload reads at every
boot, so a change applies at the next start. A missing option counts as
its default, and a slot of a release before v1.4.0 does not read the three
new ones.

| Option | Default | |
|---|---|---|
| *Network boot (iPXE)* | on | the iPXE entry of the boot menu: PXE, HTTP and iPXE scripts over the Ethernet port, with iPXE's Intel driver (the payload has no UEFI network stack) |
| *Legacy boot (CSMWrap)* | on | the CSMWrap entry: legacy BIOS boot, refused while Secure Boot is on |
| *Option ROMs of the cards* | *All* | from v1.4.0 (patch 0178, `edk2/0036`): the UEFI drivers in the option ROMs of the PCIe cards, which the firmware runs (with Secure Boot on, only those that the db keys allow); *Graphics cards only*: just those of display controllers |
| *Boot from USB drives* | on | from v1.4.0 (0178, `edk2/0037`): off, the firmware makes no boot entry for a USB drive |
| *Boot menu prompt* | on | from v1.4.0 (0178, `edk2/0037`): off, no "Press ESC for Boot Options/Settings" on the logo, as *Option Keys Display* of the OEM setup; Esc still opens the boot menu |

- **Graphics cards only**: a graphics card on the riser still shows the
  logo, the boot menu and the setup, also without processor graphics
  ([Other processors and cards](#other-processors-and-cards)). NVMe, SATA
  (AHCI) and USB cards still boot with the firmware's own drivers, and
  Intel network cards through iPXE; a card that needs its own ROM to boot
  (RAID, SAS, other network cards) then works in the OS only, and CSMWrap
  gets no legacy ROM of a card that is not a display controller. The
  class is what the card reports: a policy, not a security boundary. There
  is no *None*: without processor graphics, or with *Intel graphics* off,
  the ROM of the graphics card is the only firmware screen.
- **Boot from USB drives off**: the entries the boot manager made for USB
  drives leave the boot order and the boot menu, deleted once (one write
  to the flash) and not made again; a USB network adapter keeps its
  network entries, and the disks, the Shell, iPXE and CSMWrap keep theirs.
  It is not a security setting: a USB drive still boots from a `Boot####`
  entry that an OS made, from *Boot From File* in the *Boot Maintenance
  Manager*, from the UEFI Shell and its `startup.nsh`, from CSMWrap, and
  through `\EFI\BOOT\BOOTX64.EFI`, which the firmware tries on every drive
  once no boot entry works. With Secure Boot on these paths start only
  signed programs, and the default keys accept those signed by Microsoft
  (Windows, shim). After a switch to a slot before v1.4.0, that slot makes
  the USB entries again, and the next boot of a v1.4.0 slot deletes them.
- An RTC power loss sets all five back to their defaults
  ([Resetting the settings](#resetting-the-settings)).

Not yet tried on the machine.

## Other processors and cards

The port machine has an i3-8100 (65 W, no Turbo Boost, no Hyper-Threading),
no card on the riser and a PCIe Wi-Fi card. The firmware reads the rest from
the hardware at each boot, so another processor or card needs no other
build:

- **Processors**: every Coffee Lake desktop one the board takes, the
  Pentium and Celeron to the eight-core Core i9 of the 9th generation, T
  (35 W) and 65 W models. The microcode in the image covers all their
  steppings (CPUID 906EA, 906EB, 906EC, 906ED), the current limits of the
  voltage regulator come from coreboot's table for the processor's host
  bridge and TDP, and the firmware supports up to 16 threads.
- **Power limits**: PL1 is the TDP, PL2 1.25 times it, as with the OEM
  firmware (*Energy Saver* → *Processor*: 0 in both options). Up to rc3 PL2
  was 65 W for every processor; a machine that saved its settings then
  keeps that value until the option is set back to 0.
- **Fan**: the EC gets the class of the sustained power, the TDP or the
  PL1 of the option (35, 45, 65 W or more), and picks its fan table from
  it, as with the OEM firmware ([Fan](#fan)).
- **Turbo Boost and Hyper-Threading**: in the menu only on the processors
  that have them (Turbo Boost: not the 8th generation Core i3, the Pentium
  and the Celeron; Hyper-Threading: the 8th generation Core i7, the Core i9
  and the Pentium Gold). Hyper-Threading stays in the menu while it is off.
- **F processors** (no graphics): the screen is on a card of the riser
  only. The firmware leaves the riser port on whatever the option says, and
  EDK2 loads the card's UEFI option ROM (*Option ROMs of the cards* on
  *All* or *Graphics cards only*, [Boot options](#boot-options)), so the
  logo, the boot menu and the setup appear on it; the same with *Hardware*
  → *Intel graphics* off. Not tried.
- **Riser cards**: *Hardware* → *Devices* → *PCIe riser slot* on *Auto*
  turns the port on when the slot reports a card before the memory
  training, and off when it is empty (the package then reaches PC9). The
  empty slot is verified; a card is not yet. If one does not appear, set
  the option to *Enabled*; the boot log (`sudo cbmem -1 | grep PEG`)
  shows what the slot reported. The fan class of the EC also knows a card
  on the riser, and an NVIDIA one. A card that boots from its own option
  ROM (RAID, SAS, a network card that is not Intel's) needs *Option ROMs
  of the cards* on *All*, the default.
- **Wi-Fi**: a PCIe card on root port 6 or a CNVi card on the Wi-Fi
  controller of the PCH; *Hardware* → *Devices* → *Wireless* turns either
  off with its Bluetooth.
- **Storage**: both M.2 2280 slots (root ports 17 and 21) and the SATA
  bay; a port without a device is hidden at boot.
- **Memory**: one or two SO-DIMMs, either slot; FSP-M trains what is there.
- **Memory training cache**: kept for the processor and the
  Hyper-Threading setting it was made with (patch 0173), and from v1.4.0
  across updates ([Updates](#updates)). With another processor, or HT
  turned on or off, the next boot trains again: about 40 s with a black
  screen, once.

## Boot time

`sudo cbmem -t` gives the timeline of coreboot, and the `BS: ... times
(exec / console)` lines of `sudo cbmem -1` how much of each step went in
printing. On an M920x with 32 + 8 GB and ci-130 (rc2 level), coreboot took
about 10 s to the payload:

- **about 5 s on the serial console**: COM1 of the Super I/O, behind the
  optional connector, is a real UART, and at 115200 baud the 57 KB of a
  boot at log level DEBUG take 5 s, with or without a cable. From rc3 the
  default level is INFO, about 1 s; `cbmem -1` still has every DEBUG line,
  as the CBMEM console takes them at any level. The level is an option,
  saved with the others: on a machine that already ran ouroBIOS the saved
  one stays, set it in *Console* → *Console Log Level* (*Info*, or
  *Notice* for almost nothing on the serial port), or turn the serial
  port off in *Console* → *Serial Console* (from v1.4.0) and save the
  remaining second;
- **2 s clearing the memory**, about 0.5 s per 10 GB: *Security* →
  *Memory protection* → *Clear memory at power-on*;
- **0.5 s in the last SMI before the payload** up to ci-147: SMM read the
  *BIOS Lock* option from the flash without cache; from v1.4.0 ramstage
  gives it the value (patch 0170), and the step takes 0.25 s. With ci-149
  coreboot reaches the payload in 9.4 s instead of 10 s, at the saved
  DEBUG level;
- **15 s in FSP-M with the ME disabled**, on some boots and not others,
  the training cache valid or not (ci-150 to ci-157): FSP-M's HECI
  messages to the disabled ME got no answer and it retried them (3 tries
  of a 5 s timeout). From v1.4.0 (patch 0191), when the setup has the ME
  disabled, it does not retry them and skips the MBP read (found as
  Dasharo found its slow FSP, dasharo-issues #1874). One wait is left:
  FspMemoryInit takes 0.23 s or, on most boots, 5.23 s, as the ME
  applies its soft disable at the DRAM Init Done message and answers it
  late; FSP-M without that message hangs (test build ci-161). So with
  the ME disabled from the setup a boot takes 9.4 s or 14.4 s; with the
  ME enabled, or off by the HAP bit (written with an external
  programmer: the ME does not start and FSP-M sends it nothing), 9.4 s;
- the rest: verified boot 0.5 s, FSP-M 0.45 s (more when it trains: from
  v1.4.0 an update keeps the cache, made again only for another FSP-M,
  processor or Hyper-Threading setting), FSP-S, the devices and the
  tables.

`sudo python3 -I tools/hw-report.py` checks these numbers at every boot of a
new build: the time to the payload, and `FspMemoryInit` against the state of
the training cache ([docs/testing.md](testing.md)).

## Serial number and machine type (VPD)

As on the W541 ([docs/flashing.md](flashing.md#serial-number-and-machine-type-vpd)),
coreboot reports the machine's data from the `RO_VPD` region, which the
release images leave empty: SMBIOS has the MTM as product name, *ThinkCentre
M920x* as version and family, and the SKU in the form of the Lenovo
firmware, `LENOVO_MT_<type>_BU_Think_FM_ThinkCentre M920x`. Write it once,
with the values on the label (`MT-M 10S2-XXXXXX`, `S/N PCXXXXXX`):

```sh
sudo flashrom -p internal -r dump.rom
python3 tools/vpd.py set dump.rom -o vpd.rom --serial PCXXXXXX --mtm 10S2-XXXXXX --uuid serial
sudo flashrom -p internal --fmap-file vpd.rom -i RO_VPD -N -w vpd.rom
```

`tools/vpd.py` knows the machine types 10S1 and 10S2; for another M920x
type, add `--family "ThinkCentre M920x"`.

With the dump of the Lenovo firmware made before the [first
install](#first-install), `--from-lenovo` takes the serial number, the MTM
and the UUID that the Lenovo BIOS kept in its NVRAM (the AMI `DmiVar`
variables); the UUID is not on the label, and `--uuid serial` makes another
one. Values given on the command line win:

```sh
python3 tools/vpd.py set dump.rom -o vpd.rom --from-lenovo lenovo-dump.rom
```

If the machine came with Windows, the Lenovo BIOS also kept its product
key there (OEM Activation 3.0, the `RomHoleReplaceOA3Var` variable):
`--from-lenovo` copies it into the `msdm_product_key` key, or give it with
`--windows-key`, and ouroBIOS publishes it in an ACPI MSDM table, as the
Lenovo BIOS did (patch 0159), for Windows to activate by itself; under
Linux the table is `/sys/firmware/acpi/tables/MSDM`, which a virtual
machine can be given (QEMU `-acpitable file=...`). `vpd.py` shows only
its last group; it stays in the VPD of the machine. A capsule update leaves the VPD
alone; an update with flashrom rewrites it, so copy it first
(`python3 tools/vpd.py copy dump.rom m920x-coreboot-vX.Y.Z-fsp.rom -o m920x-flash.rom`).

## Building

```sh
tools/build.sh --board m920x prepare toolchain roms   # dist/m920x-coreboot-<version>-fsp.*
tools/build.sh --board all roms                       # every board, as the CI
```

`prepare` also fetches coreboot's `3rdparty/fsp` submodule. The images come
out in `dist/` with the W541 ones, and `tools/verify-rom.sh --board m920x
--variant fsp` checks them.
