# Patches

`series` lists the patches that `tools/build.sh` applies with `git am`, in
order, to coreboot at the commit pinned in `tools/build.sh`
(`COREBOOT_COMMIT`). Every file is a `git format-patch` mail; they are written
for upstream review (one change each, with the reasoning in the message).
`tools/coreboot-lint.sh`, in `check.yml`, holds them to coreboot's style as
Gerrit does: `util/lint/lint lint-stable` on the tree with the series, and
`checkpatch.pl` with the tree's `.checkpatch.conf` on every patch of the
project's author; an `ERROR` stops it but *Missing Signed-off-by*, which the
author adds when a patch goes upstream, and the ones listed in
`checkpatch-known.txt`: four false positives in the native RAM init
(0087-0088), the member of a compound literal, `(union ...) { ... }.raw`,
as upstream's NRI code writes it, and the sign of `+1`.

## EDK2 and LvglPkg

`edk2/` and `lvglpkg/` hold the patches to the payload: `edk2/series` on
MrChromebox's EDK2 at `EDK2_MRCHROMEBOX_COMMIT` (`tools/build.sh`),
`lvglpkg/series` on its `LvglPkg` submodule (the graphical setup UI) at the
commit that EDK2 pins (`LVGLPKG_COMMIT`), with LVGL at `LVGL_COMMIT` (from
v1.6.0 LVGL v9.6, in place of the v9.5.0 of LvglPkg's own submodule: the
two trees take the same). From v1.6.0 the ROMs build from
TianoCore's tag with [`tianocore/`](#tianocore-edk-ii-for-the-package) and
the package `edk2/OuroBiosPkg`, which `tools/edk2-import.py` makes from
MrChromebox's tree with `edk2/series`: a change to the payload is a patch
here, then the import. `tools/build.sh prepare` fetches the EDK2 of the
defconfigs into the coreboot tree, where the payload build expects it, and
applies the series as changes, not commits: coreboot's EDK2 Makefile resets
a clean tree to the pinned commit but leaves a modified one alone.
`tools/edk2-patchcheck.sh`, in `check.yml`, runs EDK II's `PatchCheck.py`
on every patch of `edk2/series` of the project's author and stops when the
code does not pass it (line endings, tabs, trailing spaces...); the
message never passes it, as the author adds the Signed-off-by when a patch
goes upstream. `lvglpkg/` stays out: LvglPkg keeps LF line endings.

## The update test

`test/q35-update-test.patch` is not a coreboot change for the W541:
`tools/build.sh update-test` applies it to a git worktree of the coreboot
tree of its own, which only builds the q35 images of the update test in QEMU
(`tools/qemu-update.py`, [docs/vboot.md](../docs/vboot.md#how-it-is-tested));
the tree of the ROMs never sees it. It gives q35 what an update touches on the
W541: vboot's nvdata in the flash, written by verstage from the bootblock
(on QEMU's pflash the write loops run from RAM), only the bootblock in the
read-only CBFS, and the W541's map cut down to `RW_MRC_CACHE`, `SMMSTORE`,
`RW_NVRAM`, the two RW slots and `WP_RO`.

## The setup menu and its screenshots

The W541 cannot be emulated, so neither can its ramstage, which writes the
setup menu (the CFR record) into the coreboot table. `tools/cfr-dump.sh`
builds the menu code of a W541 build on the host instead (the `cfr.c` of the
mainboard and of the H8, with the `config.h` of the build and stubs for what
reads the hardware: `tools/cfr-dump/stubs.c`), writes the record as the
ramstage does, reads it back and checks it: its structure, the tree against
the structures of the menu, every option in one card only, and every option
that the compiled sources declare in some card. `tools/build.sh menu` runs it
on each variant after `roms`, as build.yml does, and keeps the record and the
tree in `work/menu-<variant>`.

`test/q35-cfr-file.patch`, again never in a W541 ROM, makes q35 copy that
record from the CBFS file `cfr.bin` into its coreboot table, so that the
payload of the W541 shows the W541's menu in QEMU. In a git worktree of the
coreboot tree with the patch applied (`git worktree add`, `git apply`, and
`3rdparty/vboot` copied in), `tools/q35-cfr-rom.sh WORKTREE BUILD` builds
that q35 ROM with the payload of the W541 build `BUILD`, and
`tools/qemu-setup-shots.py --cfr cfr.bin ROM` takes a screenshot of the
front page and of each category, scrolled when it is taller than the
screen.

## Updating the series

After a change in a coreboot tree based on `COREBOOT_COMMIT`:

```sh
git format-patch --zero-commit -N --start-number <N> -o /path/to/ourobios/patches/ -1 HEAD
ls /path/to/ourobios/patches/0*.patch | xargs -n1 basename > /path/to/ourobios/patches/series
```

One commit at a time, with `--start-number` the number after the last
one of the series: the numbers stay as they are, and the series keeps
its order. The numbers 0064, 0097, 0098 and 0112 stay unused: patches of
earlier release candidates, dropped since (0064 of v1.3.2-rc1; 0097 and
0098, the EHCI hiding of v1.3.10-rc1, and 0112, the panel power-up at
wake, dropped in v1.3.10: the CHANGELOG tells).

An upstream change that is not merged yet, as 0185, goes in as a
cherry-pick of its patch set (`git am` of the change downloaded from
Gerrit), with the upstream author, subject, message, `Change-Id` and
`Signed-off-by` as they are; after the upstream message comes our note:
the Gerrit URL and patch set, its votes and state on the day it was
taken, how it applied, why it is here and when to drop it, then the
`TEST=` paragraph and our `Co-Authored-By` trailer. A change of ours that
it calls for goes into a commit of its own (0186 for 0185), so that the
backport stays as upstream has it. It keeps the upstream subject, so
`upstream.yml` reports it when it is merged.

The same for MrChromebox's EDK2 (a tree at `EDK2_MRCHROMEBOX_COMMIT` of
`tools/build.sh`) and for its LvglPkg (at `LVGLPKG_COMMIT`), into `edk2/`
and `lvglpkg/`, each with its own `series`; `tools/edk2-import.py` then
makes the package and `tianocore/` from them again. Leave out `MdeModulePkg/Logo/Logo.bmp`, which the payload
build overwrites with the boot splash.

Then `tools/build.sh prepare config` checks that the series apply and that
both configurations keep every option. `tools/ci-check.sh` checks that each
`series` and its files agree.
